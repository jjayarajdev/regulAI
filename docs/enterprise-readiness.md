# RegulAI — Enterprise Readiness Gap List

**Last updated**: 2026-05-19
**Purpose**: a candid inventory of what's missing between today's working vertical slice and a production deployment at an insurance carrier. Each item is sized as **load-bearing** (can't sign a customer without it), **scale-bearing** (works for one customer, breaks at three), or **nice-to-have** (polish).

**Companion docs**: [`rhs-build-summary.md`](rhs-build-summary.md) (what's actually built), [`kg-framework-assessment.md`](kg-framework-assessment.md) (Neo4j-side audit), [`business-tech-ui-map.md`](business-tech-ui-map.md) (problem → tech → UI).

---

## 1. Identity, auth, RBAC — load-bearing

**What's there**: nothing. `USER_ACTION.actor` is hardcoded ("D. Reyes", "M. Okonkwo"). Anyone hitting `/api/rhs/*` can approve any filing.

**What's needed**:
- **SSO** — SAML or OIDC against the carrier's IdP (Okta / Azure AD / Ping). ~1-3 days with `fastapi-users` or `authlib`.
- **RBAC** — `analyst | actuary | officer | viewer | admin` roles enforced **on the API**, not just the UI. Today the approve endpoint trusts the `role` field in the request body, which is exactly backwards.
- **Per-filing scoping** — some users see only HO, some only commercial, some only TX. Add `permitted_filings` to the user model + `WHERE filing_id IN (…)` to every endpoint.
- **API tokens** — for service-to-service (Snowpipe trigger → API, TICO ACK webhook → API). Short-lived JWTs or static API keys with rotation.
- **`USER_ACTION.actor` becomes the authenticated user**, not a label. The audit chain is only defensible if this is real.

**Est. effort**: 1-2 weeks for a competent backend dev. The Pydantic models + dependency-injection pattern in FastAPI make this clean to retrofit.

## 2. Multi-tenancy — load-bearing for customer #2

**What's there**: everything lives in one Snowflake database, one Neo4j, one global `FILINGS` registry hardcoded in `packages/rhs/filings.py`.

**What's needed**:
- **`carrier_id` / `tenant_id`** column on every GOLD + audit table; row-level filtering on every query.
- **Snowflake row-level security policies** or per-tenant schema strategy.
- **Per-tenant Neo4j**, or label-scoped graphs within a shared Neo4j (`(:Rule:Tenant_acme)`).
- **Filing registry in DB** — `FILING_REGISTRY` table replacing the hardcoded Python list. Admin UI to add filings.
- **KG-side multi-tenancy** — currently a single canon serves all customers. Each customer's bulletin history needs isolation.

**Caveat**: TX residential plan rules are the same for every TX carrier — the canon is genuinely shared. Customer isolation matters for **filings**, **violations**, and **submissions** — not the regulation itself. That's an architecturally clean split.

**Est. effort**: 2-3 weeks if done cleanly from the start. Painful retrofit later.

## 3. Real Guidewire integration — load-bearing for first pilot

**What's there**: `generate_bronze_data.py` produces synthetic Parquet matching the GDP schema byte-for-byte.

**What's needed**:
- **Snowpipe + S3** pointed at the carrier's Guidewire Data Platform bucket. Schema is already byte-identical — this is configuration, not code.
- **CDC handling** — Bronze already has `_cdc_operation` columns; need MERGE-based upsert logic in Silver to handle UPDATE and DELETE events, not just INSERTs.
- **Late-arriving data** — claims reported after the period cut-off. Need a `_reporting_lag_handled` flag + retro-fill logic.
- **Source reconciliation** — compare BillingCenter premium totals against PolicyCenter and flag mismatches before they hit Silver.

**Est. effort**: 2-3 weeks per carrier; mostly Snowpipe config + customer-specific edge cases.

## 4. CI/CD — load-bearing once >1 engineer commits

**What's there**: `make test`, local `uv`. Three branches (`feature/ui-designs`, `dev`, `release`) maintained by hand.

**What's needed**:
- **GitHub Actions** running `pytest tests/ -v` on every PR.
- **Migration check in CI** — apply `materialized/migrations/*.sql` to a dedicated test Snowflake account on every PR.
- **Containerized deploy** — Dockerfile for API + UI; deploy to ECS/Fargate, k8s, or Snowflake Native Apps.
- **Staging environment** — same migrations applied to a separate Snowflake DB before prod promotion. Gated by smoke tests.
- **Dependabot + `pip-audit`** for vuln scanning on every PR.
- **OpenAPI spec auto-generated by FastAPI** (already free — just `app.openapi()`); publish `/docs` for consumers.

**Est. effort**: 3-5 days for the bones; ongoing maintenance.

---

## 5. Observability — load-bearing for ops

**What's there**: `print()` statements. Nothing more.

**What's needed**:
- **Structured logging** — replace `print` with `structlog`, JSON output to stdout for log aggregator (Datadog, Splunk, CloudWatch).
- **Metrics** — Prometheus scrape endpoint surfacing: validation latency p99, exception count per filing, sealed-but-not-ACKed gauges, anomaly-detection runtime, KG query latency.
- **OpenTelemetry tracing** — span every `/validate` call so slow rules are findable.
- **Alerting** — page someone when a filing is `submitted` >24h without an ACK; alert on validation latency >30s; alert on rule SQL errors.
- **Per-filing dashboards** — Grafana with the existing audit data. Pass rate over time, blocker count, sign-off velocity.

**Est. effort**: 1 week for instrumentation, ongoing tuning.

## 6. Data governance & retention — load-bearing for SOC 2

**What's there**: nothing enforced.

**What's needed**:
- **PII tagging** — Snowflake `OBJECT TAGGING` on policy_number, claimant fields, NAIC, ZIP. Drives masking policies for non-prod environments.
- **Retention enforcement** — TICO requires 25-month retention; add a `purge_after` column on `FILING_SUBMISSION` + a scheduled task that DELETEs aged records.
- **Right-to-erasure** — if state laws demand GDPR-like erasure of declined applicants, the system needs an endpoint that tombstones across Bronze + Silver + Gold + audit while preserving aggregate integrity.
- **Data lineage** — make the provenance columns (`kg_canon_version`, `kg_source_document_id`) navigable in a lineage UI.
- **Data classification** — public / internal / confidential / restricted, with column-level enforcement.

**Est. effort**: 1-2 weeks of focused effort + ongoing policy management.

## 7. Production-grade frontend — scale-bearing

**What's there**: 5,100-line vanilla HTML/JS in a single file, no build step, no framework, no tests.

**What's needed (in priority order)**:
1. **Error boundaries** — JS errors today silently break the page. Wrap critical render calls in `try/catch` with a fallback banner. Half-day.
2. **TypeScript + build step** — port `workstation.html` into a Vite + React/Svelte project. ~3 weeks for full refactor + better long-term maintainability.
3. **Component tests** — Playwright for E2E, Vitest for units. The current "open browser, click around" smoke test won't scale.
4. **Accessibility audit** — keyboard nav, screen-reader labels, contrast. Currently fails several WCAG 2.1 AA criteria.
5. **Responsive design** — workstation is desktop-only. Officers reviewing on iPad isn't unusual.
6. **Internationalization** — extract strings; even English-only at launch, structure should be there for Spanish (huge TX market).
7. **Crash reporting** — Sentry or equivalent so frontend errors reach someone.

**Est. effort**: 4-8 weeks total; can be done incrementally.

## 8. Secret management — load-bearing

**What's there**: `.env` files (gitignored locally) + `~/.snowflake/config.toml`.

**What's needed**:
- **AWS Secrets Manager / HashiCorp Vault** integration for production credentials.
- **Snowflake PAT rotation** automation — currently manual.
- **Per-environment credential isolation** — dev creds can't reach prod ever.
- **OpenAI / Anthropic API key rotation** for Sentinel.

**Est. effort**: 2-3 days.

---

## 9. API maturity — scale-bearing

**What's there**: 30 endpoints, mostly clean shape.

**What's needed**:
- **Versioning** — `/api/v1/rhs/...`; older clients keep working when the schema changes.
- **Rate limiting** — `slowapi` or NGINX-level; protects against runaway `/validate` calls.
- **Idempotency keys** on POSTs (`/approve`, `/ack`, `/file?persist=true`) so a network retry can't double-submit.
- **Tighter request validation** — currently partial; tighten body schemas with Pydantic.
- **Webhook system** — outbound event bus for "filing submitted", "ACK received", "bulletin applied". Drives Slack/email/customer-system integrations.
- **Long-running job pattern** — `/anomalies/detect` and `/bulletin/apply` are sync; should be `POST → 202 Accepted` with a task_id + polling endpoint for status.

**Est. effort**: 1-2 weeks.

---

## 10. Real TICO + bulletin integrations — load-bearing for production filing

**What's there**: synthetic ACK button, manually-dropped bulletin files.

**What's needed**:
- **TICO ACK webhook** — inbound endpoint with HMAC signature verification (whatever scheme TICO uses).
- **TDI bulletin poller** — scheduled job hitting the Commissioner's Bulletin RSS, downloading new bulletins, running Sentinel extraction, queueing for HITL approval before they flip the canon.
- **Calendar awareness** — filing due dates differ by plan; system should know quarter-end / month-end and pre-warn 30/15/7 days out.
- **Submission retry policy** — what happens when TICO ShareFile is down at submission time.

**Est. effort**: 1 week per integration once the spec is in hand.

---

## 11. Performance & scale testing — scale-bearing

**What's there**: works fine at 371 policies + 154 claims.

**What's needed**:
- **Load test at 1M policies, 500K claims** — Snowflake queries are usually fine but the API renders the full violations list in a single payload. May need pagination at the API or aggregation at the DB.
- **Materialized validation results** — running 14 rules × 1M records on every UI refresh isn't free; cache the latest run.
- **Snowflake clustering keys** on `filing_batch_id`, `policy_number`, `rule_id` for the GOLD tables.
- **Connection pooling** — `snowflake_client.query()` opens a new cursor every call; pool the connections.
- **Validation parallelism** — currently rules execute serially; could parallelize 14 rules across threads.

**Est. effort**: 1-2 weeks.

## 12. Compliance & security audits — load-bearing for enterprise sale

If selling to carriers, you'll need:
- **SOC 2 Type II** — 6-12 months of audit-log retention + formal controls inventory. The audit chain we built is the foundation, but you need policies on top.
- **Penetration test** — third-party engagement before first customer.
- **Code review checklist** — formal PR process with security gating.
- **Privacy review** — what regulator + customer data we hold, for how long, who can access.
- **Disaster recovery runbook** — what to do when Snowflake region goes down, when Neo4j corrupts, when an LLM extraction misfires.

**Est. effort**: 6-12 months of process + audit, mostly external.

## What I'd defer / not do for v1

- **Native mobile app** — laptop+iPad responsive is enough; native apps are overkill for compliance officers.
- **Real-time websocket push** — UI polling on user action (the current model) is fine for an internal tool.
- **GraphQL surface** — REST + OpenAPI is sufficient; GraphQL adds operational complexity without enabling new use cases here.
- **Custom rule authoring UI** — let customers contribute rules via PR for the first year, not a UI.
- **Self-service customer signup** — enterprise sales motion is high-touch; no public signup needed for years.
- **Multi-region failover** — Snowflake's own replication is fine for years; bespoke active-active is over-engineering.

## What "production-ready" actually means here

Three independent definitions:

1. **Engineering-ready** — items 1, 4, 5, 8, 11, 13 (auth, CI, logs, secrets, scale, KG hygiene).
2. **Customer-ready** — items 2, 3, 7, 9, 10 (multi-tenant, GDP integration, frontend polish, API maturity, TICO live).
3. **Compliance-ready** — items 6, 12 (governance, SOC 2, pen test).

A pilot can launch with engineering-ready + a minimal slice of customer-ready (one customer, one filing, manual integration). Real production requires all three.

The vertical we've built is the **proof the architectural thesis works**. The above is the work to make it durable.
